# セキュリティ設計

## 保護するものと保証の範囲

保護対象はWindows上のファイル、起動中アプリ、入力内容、クリップボード、ターミナル、画面、端末登録情報、TLS秘密鍵。攻撃者として、未登録のLAN端末、悪意あるWebページ、盗聴・DNS改変、紛失したiPhone、誤設定を想定する。

**通常操作は非管理者で動かす。ただし、自由なシェルと画面操作を許した端末は、現在のWindowsユーザー相当の操作主体である。** ファイルAPIの許可ルート、起動アプリのリスト、アプリ内確認は、自由なシェルや任意のデスクトップ入力に対するサンドボックスにはならない。作業フォルダ指定やPowerShell ExecutionPolicyも隔離境界として使わない。

次のことは、このアプリだけでは保証しない。

- 侵害済みのWindowsユーザーや管理者からの防御。管理者はFirewall・バイナリ・設定を書き換えられる。
- シェル利用者が別のサーバーや外向きトンネルを起動することの完全禁止。GUI経由でも実行環境へ到達し得る。
- 侵害済みの登録iPhoneや、登録端末が行う中継を、正規の操作と完全に区別すること。
- iOS・Windows自体、第三者ソフトウェア、ルーターの未知の脆弱性からの完全な保護。

もし「自由なPowerShellでも、指定フォルダ外・外向き通信・設定変更を絶対に禁止」が必要なら、別Windows標準アカウント、ACL、独立した実行環境、ネットワーク側の制御を追加する必要がある。現在のデスクトップをそのまま操作する利便性とは両立しない部分があるため、別設計として判断する。

## LAN限定を維持する多層防御

「プライベートIPだから安全」「ルーターで転送していないから安全」だけに依存しない。

| 層 | 必須の設計 |
| --- | --- |
| 待受け | セットアップで選択した物理NICと、そのNICの固定IPv4にだけ明示bind。`0.0.0.0`、`::`、ホスト名による曖昧なbindを禁止 |
| ネットワーク識別 | NICの識別子、登録ネットワーク、ローカルIPv4、プレフィックス、Privateプロファイルを照合。SSID名だけを信頼しない |
| 接続元 | 登録した自宅の具体的CIDR内か確認し、通常運用は登録iPhoneのIPv4 `/32`にも限定。IPは補助条件で、認証の代わりにしない |
| Windows Firewall | 既定の受信拒否を維持し、アプリ・TCPポート・ローカルIP・NIC・Private・送信元を絞った許可を1つ作る。edge traversalをBlockにする |
| IPv6 | MVPのこのアプリはIPv6ソケットを開かない。OS全体のIPv6を無効化する設計ではない |
| 認証 | 許可ネットワークでも未登録端末は操作不可。IPやMACの一致だけでは認可しない |
| 外部経路 | UPnP、NAT-PMP、PCP、STUN/TURN、外部ID・relay、VPN連携、公開URL、リバーストンネルをアプリ機能として持たない |
| プロキシ | 外部reverse proxyを前提にしない。`Forwarded` / `X-Forwarded-For`で接続元を上書きしない。通常の入口でloopbackやゲートウェイ経由を許可端末扱いしない |
| 設定変更 | 起動前と稼働中に実効設定を点検。不一致・検査不能なら新規待受けを拒否し、既存接続を閉じる |

Kestrelは指定の仕方によって全IPにbindするため、`https://my-pc:8443`という名前を書くだけではNIC制限にならない。[Kestrelの仕様](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0) FirewallはInterface・RemoteAddress等の条件を使える。[New-NetFirewallRule](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule)

初回はiPhoneの現在IPをPCで選び、ルーターのDHCP予約でPCとiPhoneのIPを安定させる案を推奨する。これはポート転送ではない。予約できない場合、IPが変わるたびにPC側で登録を確認し直す。利便性のために接続元を`Any`へ自動拡張しない。ルーターの全設定や他機器の通信設定はアプリから変更しない。

Firewallでは「全通信Blockと例外Allow」を重ねればよいとは限らず、明示BlockがAllowを打ち消す。重複ルールも含めた実効ポリシーで確認する。Public/Domain上のアプリ受信禁止と、Private上の限定許可を明確にする。他アプリのFirewallルールを削除しない。

ネットワーク変更通知、復帰、設定変更ごとに再検査し、通常時も監視する。既存のWSSにも適用する。登録条件が崩れたら「自宅ネットワークを確認してください」とPCに表示し、広いbindへ切り替えない。イベント検出までの時間をゼロと保証せず、変更検出後の切断目標を検証する。

NAT転送で外部の送信元がそのまま見える場合は送信元検査で拒否できる。一方、信頼した端末上のプロキシで送信元を隠された場合はネットワーク条件だけでは識別できない。TLS・端末認証を重ねても、認証済み端末そのものの悪意ある中継までは防げない。

## 安全な設定の固定

- 待受け、許可NIC、IPv6禁止、TLS必須、リレー禁止、VNCループバック限定は安全性に関わる固定条件とする。Webの設定画面に「WANを許可」「認証なし」「TLSなし」を作らない。
- `ASPNETCORE_URLS`、汎用Kestrel設定、コマンドライン引数で固定条件が上書きされないよう、最終的な全endpointを起動前に検証する。未定義の追加endpointがあれば起動拒否。
- プログラムとネットワーク許可ポリシーは、標準ユーザーが書き換えられないインストール先／ACLで保護する。変更はPC上のセットアップ処理で行う。
- 端末登録DB等のユーザーデータは別に置く。通常ユーザー権限の任意コードがこのDBを改変できる場合があることを前提にし、同一ユーザー侵害を防げるとは主張しない。
- VNCの設定だけでなく実待受けとプロセス状態を確認する。安全な起動が検証できなければ画面操作だけを利用不可にする。

## TLSと証明書の初期導入

**HTTPS/WSSを必須にする。証明書警告を無視した接続、HTTPへの自動切替、自己署名証明書の無検証受け入れは提供しない。**

1. PCのセットアップで、この用途専用のローカルCAとサーバー証明書を作る。作成・検査はOSSのstep CLIを用い、CAサーバーやSmallstepのクラウドサービスは導入しない。[step CLI](https://smallstep.com/docs/step-cli/reference/certificate/create/) [Windows対応](https://smallstep.com/docs/step-cli/installation/)
2. サーバー証明書のSANには登録したPCのIPv4を入れる。固定IPのHTTPS URLをMVPの正規オリジンにする。公開DNS・ドメイン取得・mDNS探索は必須にしない。
3. CAの公開証明書だけをiPhoneへ渡す。USB等で真正性を確認できるファイル転送を第一候補とし、PCに表示するSHA-256フィンガープリントとiPhone側の証明書詳細を照合する。証明書だけのプロファイルであることも確認する。
4. iOSでインストール後、証明書の信頼を明示的に有効にする。手動導入した証明書は自動でSSL用に信頼されない。[Appleの手順](https://support.apple.com/en-us/102390)
5. 警告なしでHTTPSへ接続できることを確認し、ホーム画面追加後のPWAで端末登録する。SafariとPWAの状態共有は前提にしない。

**証明書をiPhoneへ渡して検証・導入する具体的な操作は、所有端末とWindowsの組み合わせでG1検証を行う。** Mac、MDM、有料ソフトを前提にしない。安全で再現可能な無料の手順が成立しなければ、HTTPSを弱めずにPWA案を再検討する。実装前の資料確認だけで導入完了扱いにはしない。

CAを信頼することはiPhoneの信頼ストアへ影響する。専用CAの秘密鍵が漏れると他の通信のなりすましにも悪用され得る。CAの秘密鍵をエージェントの実行ユーザー、Web配信フォルダ、Git、iPhoneへ置かない。パスフレーズで暗号化し、別管理者のアクセス制限された保管場所か既存のオフライン媒体へ退避する。保管できなければ発行後に鍵を破棄し、更新時はCAごと再導入する運用を選ぶ。追加ハードウェアを必須購入にしない。

エージェントにはサーバー証明書とその秘密鍵だけを渡し、Windowsの鍵保護とACLを使う。DPAPI等は同じユーザー権限で実行される攻撃者からの隔離を提供するものではない。証明書期限は運用値としてCA 5年・サーバー365日を初期案とし、実際のiOS検証と採用ツールの制約に合わせて確定する。30日前からPCで更新を案内し、期限切れなら停止する。

mkcertは開発用の検証には使えるが、公式自身が開発用途を前提としているため常用の自動セットアップには採用しない。[mkcertの注意](https://github.com/FiloSottile/mkcert) 秘密鍵漏えい時は端末失効だけで済ませず、iPhoneの旧CA信頼を除去してCA・サーバー証明書を作り直す。

## 端末登録とセッション

以下は設計の初期値。暗号プリミティブや独自の署名プロトコルは作らず、.NETの乱数・ASP.NET Coreの認証／CSRF／パスワードハッシュ機能を使う。

1. PCトレイで「iPhoneを登録」を開始する。既存の画面・入力・自由シェル接続をいったん閉じ、登録APIを2分だけ有効にする。
2. PCは暗号学的乱数の16文字Base32コード（80 bit）を表示する。PWAに手入力し、PC側で表示される接続要求を確認して許可する。5回の不正試行でコードを失効させ、再発行はPCで行う。
3. 成功後、256 bitの端末credentialを発行する。iPhoneには`Secure; HttpOnly; SameSite=Strict; Path=/`の`__Host-`Cookieとして保存し、サーバーにはcredentialのハッシュ・登録名・期限・失効状態を保存する。URL、ログ、localStorageへ秘密を出さない。
4. 初回PCセットアップで設定したアプリ専用パスフレーズと端末credentialの両方で操作セッションを開始する。パスフレーズは標準の適応的ハッシュで保存する。Windowsログインパスワードは入力させない。
5. 操作セッションは最大8時間、ユーザー操作なし30分で失効する。heartbeatやサーバー出力では延長しない。再開はパスフレーズの再入力を求める。端末credential自体は30日で失効し、PCで再登録する。
6. 自由シェル／画面操作はPCであらかじめ許可した機能のみ。開始時に直近の再認証を要求し、15分の操作枠を発行する。延長は明示操作とし、無期限の権限を渡さない。

長い再認証間隔への変更は将来のUX評価で検討する。WebAuthn等での端末内認証は将来候補だが、iCloud同期や外部アカウントを必須にしないことを確認してから追加する。MVPはFace IDが使えると約束しない。

Cookie登録は「そのブラウザ環境に発行した秘密を持つ」認証であり、物理的なiPhone個体への暗号学的束縛ではない。盗まれたCookieの再利用や、有効セッション中の紛失端末には残余リスクがある。

トレイの承認ボタンも物理的な本人操作を証明する装置ではない。登録中は既存リモート入力を止めるが、同一ユーザーの任意コードが既に侵害されている状態には耐えない。登録コードの有効時間・同時登録数・試行回数を制限する。

## Web経由の攻撃への対策

- TLSの認証に加えて、HTTPのHostとWSSのOriginを正規オリジンと完全一致で検査する。`null`や欠落したWebSocket Originを許可しない。ネイティブクライアントはOriginを偽装できるため、Origin検査を認証とは扱わない。
- CORSを他オリジンへ開かない。すべての変更APIにCSRF対策。CookieのSameSiteだけには依存しない。
- CSPは`default-src 'self'`を基本とし、scriptは自己配信、`frame-ancestors 'none'`、`object-src 'none'`等を設定する。例外は採用ライブラリに必要な最小限を検証し、`unsafe-eval`を安易に許可しない。
- ユーザーのファイル名、ウィンドウタイトル、端末出力をHTMLとして挿入しない。XSSは画面上の誤表示に留まらずシェル操作へ直結する。[xterm.jsの注意](https://xtermjs.org/docs/guides/security/)
- xterm.jsのリンク、OSC clipboard、カスタム制御ハンドラーを無条件に有効化しない。外部URLを自動的に開かない。
- WSS接続時だけでなく、利用枠の期限・失効・対象セッションの所有を稼働中も確認する。失効時に実接続を閉じる。Origin検査、セッション管理、メッセージ単位の認可は既存の推奨にも沿う。[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
- 制御JSONは64 KiB、テキスト入力は64 KiB、同時操作端末1台、自由PTY1本、画面接続1本を初期上限とする。ファイル転送とRFBには専用の上限・流量制御を設ける。制御メッセージの上限を大きなRFBフレームにそのまま適用しない。
- 認証失敗は端末・送信元・全体でrate limitし、レスポンスから端末登録の詳細を漏らさない。監査に本文や秘密を残さない。

## 操作別の制限

| 操作 | サーバー側で守る条件 | 残るリスク |
| --- | --- | --- |
| ファイル | ルートID、相対パス、実ハンドルの最終パス、NTFS権限、バージョン照合 | 自由シェル・GUIは同じ制限を受けない |
| パス処理 | `..`、絶対パス、UNC、デバイスパス、ADS、予約名、reparse pointを拒否。大文字小文字・区切り・短縮名も正規化 | 検査と使用の競合があるためハンドル単位で処理。パス検査だけの実装は不可 |
| ファイル変更 | ハードリンク数が複数のファイルはMVPで変更拒否。作成先の親も検査。原子的確定と競合検出 | 同一ユーザーの悪意ある並行変更まで完全隔離はしない |
| 削除 | ごみ箱へ。利用できなければ失敗とし、永久削除へ自動変更しない | バックアップの代替ではない |
| 起動 | 登録アプリと型付き引数のみ。コマンド連結・任意URL schemeを禁止 | 許可アプリ自体に任意コード実行機能があれば権限は広い |
| 終了 | 所有セッションの指定ウィンドウに通常終了要求。強制終了はMVP対象外 | 保存確認は画面操作またはPC側対応 |
| 入力 | 対象・世代・前景を確認。パスワード欄の自動収集はしない | フォーカス競合や対象アプリの予期しない解釈 |
| 定型作業 | 事前登録した固定処理と検証済み引数 | shell escapeや任意パス引数が残れば隔離にならない |
| 自由シェル・画面 | 非昇格、明示許可、短い操作枠、失効・停止 | Windowsユーザー相当。ファイルや認証DBに到達し得る |

標準ユーザーアカウントを日常利用し、管理者アカウントを設定作業用に分けることを推奨する。既存アカウントを勝手に変更しない。管理者所属アカウントの非昇格トークンで動く場合でも、UACを完全なセキュリティ境界として説明しない。

## 監査、停止、紛失、更新

- PCトレイに接続中の端末名・操作モードと「すべて停止」を常時表示する。停止は新規要求の拒否、WSS切断、PTY/VNC終了まで行う。
- ログは日時、匿名化した端末ID、操作種別、成功／拒否理由を記録し、初期案は7日保持・10 MiB上限。コマンド本文、画面、クリップボード、秘密、フルパスは既定で記録しない。
- iPhone紛失時はPCでその端末を失効させ、全セッション・全操作枠を即座に終了する。ブラウザからCookieを消すだけではサーバー側失効にならない。
- PCロック・ユーザーログオフ・ネットワーク不一致では接続を終了し、画面・自由シェルを停止する。接続断の一般的な復帰猶予とは区別する。
- アンインストールではこのアプリのFirewallルール・自動起動・設定を削除し、iPhone側のCA証明書／ホーム画面アプリの削除手順を案内する。
- 更新は手動で検証した成果物を適用する。自動更新サーバーや実行時パッケージ取得を追加しない。サーバーとPWAの版が互換でなければ操作を止めて再読込する。
- SBOM、lockfile、採用版、取得元、ハッシュを管理する。OSSの脆弱性確認は保守時に行い、アプリ自身を常時クラウドへ接続しない。

## 主なリスクの整理

| リスク | 影響 | 主な対策 | 残余・検証 |
| --- | --- | --- | --- |
| LAN内未登録端末 | PC操作・情報窃取 | TLS、登録credential、パスフレーズ、送信元条件 | G2で未認証・失効・別端末を検証 |
| 悪意あるWebページ | CSRF、WebSocket hijack、DNS rebinding | Origin/Host、CSRF、SameSite、CSP | G2で本物のブラウザから検証 |
| 誤った外部公開 | インターネットからの到達 | 固定bind、Firewall、IPv6不使用、設定不変条件 | G3。意図的な管理者変更は保証外 |
| CA秘密鍵漏えい | TLSなりすまし、他通信にも影響 | 専用CA、鍵の分離・暗号化、旧CA除去 | G1で保管と更新を検証 |
| 紛失iPhone | 保存credential・有効セッションの悪用 | 再認証、期限、PC側失効、iPhoneのロック | 有効セッション中の残余リスク |
| UIへのXSS | シェル・GUI権限の悪用 | 非HTML化、CSP、依存削減、アクティブコンテンツ禁止 | G2/G6。HttpOnlyだけではXSS操作を止めない |
| パス回避・競合 | 許可外の読取／変更 | ハンドル検査、reparse禁止、ACL、競合検出 | G5。シェルの隔離とは別 |
| VNC設定の逸脱 | 無認証または平文の画面公開 | ループバック、通常アプリ、入口検査、停止 | G7。既定値依存は禁止 |
| 誤入力・二重実行 | データ損失・意図しないコマンド | 対象確認、送信分離、操作ID、再送禁止 | G4/G8。フォーカス競合は残る |

これらは設計上の対策であり、監査済み・脆弱性なしという評価ではない。実装後の[否定ケースを含む検証](mvp-validation.md)に合格するまでは常用しない。
